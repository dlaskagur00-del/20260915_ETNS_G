## 1. 이번 요청의 목적

OFFICE HISTORY에서는 일반적인 Dashboard보다 "공간" 자체가 중요한 UI 요소다.

필요한 고품질 시각자료:

1. 3D Office / Isometric Office
2. Office Floor Map
3. 공간 이용 Heatmap
4. 가구 및 제품 이미지
5. 벽지 / 바닥재 / 파티션 / 조명 등 공간 구성 요소 이미지
6. 공간 변경 Before / After
7. AI Proposed Office
8. Project Asset 이미지

Claude가 이러한 이미지를 직접 생성하는 데 한계가 있으므로, 이미지를 임의의 CSS 도형이나 저품질 Placeholder로 대체하지 않도록 한다.

이번 작업의 목적은 "이미지를 코드로 억지로 그리는 것"이 아니라, **"외부에서 확보하거나 별도로 제작한 고품질 시각 Asset을 OFFICE HISTORY 웹서비스가 안정적으로 사용할 수 있는 구조"**를 만드는 것이다.

## 2. 가장 중요한 원칙

**절대로 다음 방식으로 시각자료를 대체하지 말 것.**

- 단순 사각형으로 책상 표현
- CSS 원형으로 의자 표현
- 검은 사각형으로 QR 표현
- 단순 SVG 도형으로 실제 제품 표현
- 임의의 아이콘으로 가구 표현
- 저품질 Placeholder 이미지
- 깨지는 외부 이미지 URL
- 텍스트가 박힌 AI 생성 이미지
- 작은 이미지를 강제로 확대
- 로봇이나 실제 물체를 단순 도형으로 표현

OFFICE HISTORY는 발표용 Prototype이지만 시각적으로 실제 B2B Enterprise SaaS / PropTech 서비스처럼 보여야 한다.

현실의 공간과 물체를 보여줘야 하는 영역은 실제 이미지 또는 고품질 렌더링 Asset을 사용한다.

반대로 버튼 / 텍스트 / Panel / Timeline / Chart / Highlight / Tooltip / Label / History UI 등은 실제 HTML/CSS Component로 구현한다.

> **REAL WORLD OBJECT / SPACE = HIGH QUALITY VISUAL ASSET**
> **DATA / INFORMATION / UI = HTML + CSS + COMPONENT**

## 3. Asset Architecture

이미지를 Component 내부에 직접 Hard Coding하지 말고 Asset Layer를 별도로 구성한다.

```
src/assets/  또는  public/assets/
  office/ floorplans/ products/ materials/ projects/ proposed/
```

현재 프로젝트 구조를 먼저 확인한 뒤 가장 자연스러운 구조를 선택한다.

## 4. Asset Metadata 구조

이미지는 단순 파일이 아니라 Metadata와 연결되어야 한다.

```ts
interface VisualAsset {
  id: string;
  type: "office" | "floorplan" | "product" | "material" | "project" | "proposed";
  name: string;
  url: string;
  thumbnailUrl?: string;
  alt: string;
  width?: number;
  height?: number;
  source?: string;
  sourceUrl?: string;
  license?: string;
  createdAt?: string;
}
```

실제 프로젝트의 TypeScript 구조가 다르다면 기존 구조에 맞게 수정한다.

## 5. Supabase Storage 사용

최종적으로 서비스에서 사용하는 중요한 이미지들은 가능하면 Supabase Storage에서 관리한다. 외부 사이트 URL을 그대로 Production UI에 Hotlink하지 않는다.

```
외부 Asset 확인 → 사용 가능 여부 / License 확인 → Asset 확보
→ 이미지 최적화 → Supabase Storage 업로드 → DB에 Metadata 저장 → Frontend에서 URL 조회
```

```
Bucket: office-history-assets
  office/ floorplans/ products/ materials/ projects/ proposed/
```

## 6. Asset Database

필요하다면 Supabase에 `visual_assets` 테이블을 추가할 수 있다.

```
id / asset_type / name / storage_path / public_url / thumbnail_url / alt_text
source / source_url / license / width / height / metadata(jsonb) / created_at / updated_at
```

단, 현재 Supabase Schema를 먼저 확인하고 기존 구조와 중복되는 Table이 있다면 새 Table을 무조건 만들지 않는다.

## 7. 3D OFFICE VISUAL

공간 구성 History의 핵심 화면에는 고품질 3D Office 또는 Isometric Office Visual이 필요하다.

목적은 실제 3D Engine 구현 자체가 아니다. 사용자가 `Office → 공간 → 구성 요소 → History` 순서로 탐색하는 경험을 만드는 것이 목적이다.

따라서 MVP에서는 **고품질 Isometric Office Image + HTML Interactive Overlay**를 우선 고려한다.

## 8. 3D OFFICE 공간 선택

Office Image 위에 공간별 Interactive Area를 배치한다.

사용자가 공간을 Hover하면 공간명 / 현재 상태 / 간단한 이용률 정도를 Tooltip으로 보여줄 수 있다. Click하면 해당 공간을 선택한다.

선택된 공간은 Orange Outline, Semi-transparent Overlay 등 **절제된 Highlight**로 표시한다. 과도한 Neon Effect는 사용하지 않는다.

## 9. Hotspot 데이터 분리

Hotspot 좌표를 JSX에 직접 박지 않는다. 별도 데이터로 관리한다.

```js
const officeHotspots = [
  { id: "meeting-room-a", name: "회의실 A", x: 24, y: 18, width: 15, height: 20 },
  { id: "open-desk-a", name: "Open Desk A", x: 42, y: 32, width: 24, height: 30 }
];
```

좌표는 가능하면 percentage 기반으로 관리한다. 그래야 Responsive Layout에서도 이미지와 Hotspot 위치가 함께 변경된다.

## 10. Floor Map

공간 이용 History에서는 3D Office보다 Floor Map이 중심이다. 고품질 Floor Plan Image를 사용하고 그 위에 Interactive Overlay를 배치한다.

3D Office에서 사용하는 Space ID와 Floor Map에서 사용하는 Space ID는 **동일하게 유지**한다. 그래야 공간 구성 History ↔ 공간 이용 History를 같은 Space 기준으로 연결할 수 있다.

## 11. Heatmap

**Heatmap 자체를 이미지에 박아넣지 않는다.** 가능하면 Floor Map 위에 별도의 Overlay Layer로 구현한다.

```
Floor Plan + Space Overlay + Usage Heatmap + Selected Space + Label
```

이렇게 하면 Usage Data가 변경될 때 Heatmap도 동적으로 변경할 수 있다.

## 12. 공간 구성 요소 이미지

공간 구성 History에는 실제 제품이나 소재 이미지가 필요하다. (회의 테이블 / 의자 / TV / 조명 / 파티션 / 바닥재 / 벽지 / 문 / 천장 마감 / 시설·설비)

이것들을 단순 아이콘으로 대체하지 않는다. Detail Panel에서는 실제 제품 또는 소재 Thumbnail을 보여준다.

## 13. Product Asset 구조

```ts
interface ProductAsset {

  category: "furniture" | "lighting" | "partition" | "floor" | "wall" | "door" | "equipment";
  name: string;
```

현재 기존 SpaceAsset Type이 있다면 **중복 Type을 만들지 말고 확장하거나 연결**한다.

## 14. 실제 제품 이미지와 Demo 이미지 구분

실제 브랜드 제품 이미지를 사용할 경우 해당 이미지의 사용 조건을 확인해야 한다. 발표 Prototype이라고 해서 인터넷 이미지를 무조건 다운로드해서 사용하지 않는다.

우선순위:

1. 직접 제작하거나 사용 권한이 명확한 이미지
2. 라이선스가 명확한 Stock / CC Asset
3. 공식 제조사에서 제공하는 Product Media 중 사용 가능한 범위의 이미지
4. AI로 별도 생성한 Generic Product Render

실제 브랜드 제품을 사용하지 않아도 되는 Demo에서는 "Generic Modern Meeting Table" 같은 가상의 Product Asset을 사용하는 것도 가능하다.

## 15. Material Library

벽지, 바닥, 마감재 등은 Material Library 형태로 구성할 수 있다.

```
material-floor-oak-01 / material-wall-white-01 / material-partition-glass-01 ...
```

각 Material에는 name / category / textureUrl / thumbnailUrl / manufacturer / model / installedAt / vendor / price / note 등을 연결할 수 있다.

## 16. Before / After

공간 변경 History에서는 Before / After 이미지가 중요하다.

두 이미지는 가능하면 **같은 공간, 같은 카메라 Angle, 비슷한 Lighting**을 사용한다. 그래야 사용자가 공간의 변화를 직관적으로 비교할 수 있다.

## 17. AI Proposed Office

AI Insight에서 공간 개선안을 제안하면 Current / Proposed 형태로 보여준다.

**중요**: Proposed 이미지는 단순히 다른 Office Stock Image를 보여주는 것이 아니다. 가능한 한 같은 공간 / 같은 카메라 Angle / 같은 구조를 유지하면서 Layout만 변경된 것처럼 보여야 한다.

이 Visual은 실제 AI 이미지 생성 도구를 통해 별도로 생성한 후 Supabase Storage에 저장해서 사용하는 방식을 고려한다.

## 18. 이미지 생성과 웹 개발을 분리

Claude가 웹 개발 중에 이미지가 필요하다고 해서 임의의 저품질 Placeholder를 만들지 않는다. 이미지가 필요한 경우 Asset Requirement를 명확하게 남긴다.

```
ASSET_REQUIRED: office_isometric_main
TYPE: 3D OFFICE
PURPOSE: 공간 구성 History 메인 화면
RECOMMENDED SIZE: 2400 x 1600 이상
BACKGROUND: Light / Neutral
TEXT IN IMAGE: NONE
PEOPLE: NONE
CAMERA: Isometric
IMPORTANT: 회의실 / Open Desk / Lounge / Reception이 시각적으로 명확하게 구분되어야 함
```

## 19. Asset Manifest

프로젝트에 필요한 모든 Visual Asset을 Manifest(`visual-assets.json`)로 관리한다.

```json
{
  "office_isometric_main": { "status": "ready", "type": "office", "url": "...", "purpose": "Configuration History" },
  "meeting_room_a_proposed": { "status": "required", "type": "proposed", "purpose": "AI Insight" }
}
```

이렇게 하면 이미지가 없는 영역을 임의의 저품질 Placeholder로 대체하는 것을 방지할 수 있다.

## 20. Asset Placeholder 규칙

아직 이미지가 없는 경우 **가짜 이미지를 만들어 넣지 않는다.** 명확한 Placeholder Component를 사용한다.

```jsx
<AssetPlaceholder assetId="meeting-room-a-proposed" label="Proposed Office Visual" />
```

디자인은 단순하고 깔끔하게 한다. Development Mode에서만 "Visual Asset Required" 표시를 할 수 있다. 최종 Demo에서는 모든 핵심 Placeholder가 제거되어야 한다.

## 21~24. Python Image Pipeline

Python은 Visual Asset Pipeline을 자동화하는 데 사용할 수 있다.

```
scripts/images/
  optimize_images.py / generate_thumbnails.py / validate_assets.py / build_manifest.py
```

**목적**: 원본 이미지 → 크기 확인 → 필요시 Resize → WebP 변환 → Thumbnail 생성 → Metadata 출력

현재 Python Dependency를 먼저 확인하고, 필요한 Package가 없다면 설치 전에 알려준다.

**Thumbnail 구조 예시**

```
Original  office_main.png   2400 x 1600
Web       office_main.webp  1920 x 1280
Thumb     office_main_thumb.webp  480 x 320
```

**Asset Validation** — 파일 존재 여부 / Width / Height / Aspect Ratio / 파일 용량 / 지원 Format / Thumbnail 존재 / Manifest 등록 여부

최소 권장 해상도: Office Main 1600px / Floor Map 1600px / Before·Proposed 1400px / Product 800px / Thumbnail 320px

## 25. 저해상도 이미지 금지

이미지가 작은 경우 CSS로 강제로 확대하지 않는다. 원본 해상도가 부족하면 **Asset을 교체한다.**

## 26~28. Responsive · Loading · Error

- Next.js를 사용한다면 `next/image` 사용을 고려한다. 아니라면 해당 Framework의 최적화 방식을 따른다.
- 메인 Office Image와 Floor Map은 Loading UX도 고려한다: Skeleton → Image Load → Overlay 활성화. 이미지 Load 전에 Hotspot이 이상한 위치에 표시되지 않도록 한다.
- 이미지가 깨졌을 때 브라우저의 Broken Image Icon을 그대로 보여주지 않는다. Fallback Component를 구현하되, Fallback을 실제 Demo의 정상 상태처럼 사용하지 않는다.

## 29. Visual Asset과 History 연결

Visual Asset은 단순 Decoration이 아니다. History와 연결되어야 한다.

```
회의실 A → 현재 3D Visual → 회의 테이블 선택 → SpaceAsset → SpaceChangeHistory
→ 2025.03 테이블 교체 → Before Image → After Image → 교체 사유 → 비용 → 업체
```

## 30~32. 화면별 예시 / OFFICE HISTORY 연결

**공간 구성 History**: 회의실 A 클릭 → 3D 공간 Highlight → 회의 테이블 선택 → 우측 Panel(현재 이미지 · 제조사 · 모델 · 설치일 · 가격 · 교체 사유 · 특이사항) → 아래 Timeline → History Event 클릭 시 Before / After 이미지

**공간 이용 History**: Floor Map에서 회의실 A 클릭 → Highlight → 우측 Panel(이용률 72% · 평균 4.2명 · 체류 48분 · Peak 14:00~16:00) → 최근 6개월 이용률 Chart. Heatmap은 Usage Data에 따라 동적으로 변경.

**전체 연결**: 공간 구성 History(2026.06.01 8인→12인, 비용 31,200,000원) → 공간 이용 History(변경 전 4.1명 → 변경 후 4.3명) → AI Insight → Proposed Visual(12인 1개 → 6인 2개) → 예상 비용(2,800~3,200만원)

이 전체 Flow가 실제 Visual Asset과 연결되어야 한다.

## 34. 보안 및 Copyright

외부 Asset을 자동으로 수집할 경우 무조건 License / Source를 확인한다. 불명확한 이미지를 무단으로 Production Asset으로 저장하지 않는다.

Asset Metadata에 source / sourceUrl / license를 저장한다. 외부 사이트에 과도한 자동 요청을 보내는 Scraper를 만들지 않는다. robots.txt 및 사이트 이용 조건을 존중한다.

실제 ETNERS 내부 도면·견적·업체 정보·공간 정보는 사용하지 않는다. Prototype에서는 Demo Data와 Demo Visual을 사용한다.

## 35~36. Vercel / GitHub

Vercel에는 대용량 원본 Asset을 무조건 포함하지 않는다.

```
Frontend → Vercel
Visual Asset → Supabase Storage
```

대용량 이미지 원본을 GitHub Repository에 무조건 Commit하지 않는다. Git에는 Source Code / Asset Manifest / 필요한 소형 Public Asset 정도만 관리한다.

## 37. 개발 환경

## 41. 이미지가 없다고 임의로 만들지 말 것

Claude가 직접 고품질 Visual을 만들 수 없는 경우 **절대로 CSS 도형이나 저품질 SVG, 의미 없는 Placeholder Image로 최종 UI를 완성했다고 판단하지 마라.**

대신 "이 Asset이 필요하다."라고 명확하게 알려준다. 그리고 Asset ID / Purpose / Recommended Resolution / Composition / Camera Angle / Background / Required Objects / Forbidden Elements를 포함한 Asset Specification을 작성한다.

그 Specification을 이용해 별도의 Image Generation Tool에서 Asset을 생성한 후 프로젝트에 추가할 것이다.

## 43. 가장 중요한 제품 철학

이 프로젝트의 핵심은 3D가 아니다. AI도 아니다. Dashboard도 아니다. **핵심은 History다.**

```
공간 구성 History "무엇이, 언제, 왜 바뀌었는가?"
+ 공간 이용 History "누가, 얼마나, 어떻게 사용했는가?"
= OFFICE HISTORY
```

- 3D Office는 공간 구성 History를 탐색하는 Interface다.
- Floor Map / Heatmap은 공간 이용 History를 탐색하는 Interface다.
- AI는 축적된 History를 분석하여 담당자의 판단을 돕는 보조 기능이다.

따라서 항상 **HISTORY > AI** 원칙을 유지한다.

> "사무환경의 경험을 일회성 업무가 아닌, 다음 판단을 위한 데이터로."
> **"개인의 센스를 조직의 데이터로."**
