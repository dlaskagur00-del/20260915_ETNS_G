# OFFICE HISTORY 웹 프로토타입 개발 요청서

> 사용자가 제공한 원본 요청서입니다. 작업 중 판단 기준이 되는 문서이므로 내용을 수정하지 마세요.

## 0. 요청 목적

사무환경 담당자가 사무실의 "공간 변화 이력"과 "실제 공간 이용 이력"을 하나의 서비스에서 관리하고 조회할 수 있는 웹 기반 프로토타입을 개발하고 싶습니다.

서비스명은 "OFFICE HISTORY"입니다.

이 프로젝트는 실제 발표에서 직접 시연할 수 있는 프로토타입을 목표로 합니다. 따라서 단순한 정적 디자인이나 이미지가 아니라, 사용자가 공간을 클릭하고 History를 조회하며 데이터를 변경해서 볼 수 있는 인터랙티브한 웹 애플리케이션이어야 합니다.

중요한 점은 이 프로젝트가 단순한 관리자 Dashboard, 자산관리 시스템, 3D Office Viewer, AI Dashboard가 아니라는 것입니다.

OFFICE HISTORY의 핵심은 다음 두 가지 History입니다.

1. **공간 구성 History** — "공간이 언제, 무엇이, 왜 변경되었는가?"
2. **공간 이용 History** — "공간이 실제로 언제, 얼마나, 어떻게 사용되었는가?"

그리고 최종적으로

> 공간 구성 History + 공간 이용 History = OFFICE HISTORY

라는 개념으로 연결합니다.

공간의 변화와 사용 경험을 조직의 데이터 자산으로 축적하고, 축적된 History를 향후 공간 변경, 레이아웃 개선, 비용 검토 등의 의사결정에 활용하는 것이 서비스의 목적입니다.

## 1. 가장 중요한 제품 원칙

이 프로젝트에서 가장 중요한 것은 "History"입니다.

3D Office, Floor Map, Dashboard, AI는 History를 더 쉽게 이해하고 활용하기 위한 수단입니다.

따라서 일반적인 관리자 Dashboard처럼 카드와 숫자만 나열된 화면으로 만들지 마세요.

사용자가 서비스를 보자마자 "공간을 클릭하면 이 공간이 어떻게 변해왔고, 실제로 어떻게 사용되어 왔는지 알 수 있구나."라고 이해할 수 있어야 합니다.

핵심 UX Flow:

```
공간 선택 → 현재 공간 상태 확인 → 공간 구성 History 확인
→ 공간 이용 History 확인 → 두 History 연결 → AI Insight 확인 → 공간 개선안 검토
```

## 2. 서비스 전체 구조

좌측 Sidebar Navigation 기반의 B2B SaaS 형태로 구성해주세요.

```
OFFICE HISTORY
- Dashboard
- Office History
  - 공간 구성 History
  - 공간 이용 History
- AI Insight
- Project Asset
```

MVP 우선 구현 화면: Dashboard, 공간 구성 History, 공간 이용 History, AI Insight, Project Asset

중요도 순서: 공간 구성 History → 공간 이용 History → 두 History의 연결 → AI Insight → Project Asset

## 3. Dashboard

Dashboard의 목적은 복잡한 BI 분석이 아닙니다. 현재 Office의 상태와 최근 History를 빠르게 확인하는 화면입니다.

상단에는 관리 중인 Office 정보를 표시합니다.

```
ETNERS OFFICE
전체 공간  24 / 회의실 8 / 업무 공간 10 / 공용 공간 6
```

화면의 중심에는 Office 전체 Floor Map 또는 3D Office를 크게 보여주세요. 공간 자체가 화면의 주인공이어야 합니다.

아래 또는 우측에는 최근 공간 History를 보여주세요.

```
[최근 공간 History]
2026.08.21  회의실 A      테이블 교체
2026.07.13  Open Desk B  좌석 16석 → 20석 변경
2026.06.02  라운지        바닥 마감재 교체
```

별도 영역에는 최근 공간 이용 현황을 보여주세요.

```
[이번 달 공간 이용]
전체 공간 이용률  72%
회의실 이용률     68%
업무공간 이용률   81%
공용공간 이용률   54%
```

## 4. 공간 구성 History

이 화면의 핵심 질문: **"이 공간이 어떻게 바뀌어 왔는가?"**

메인 화면에는 고품질 3D Office 또는 Isometric Office Map을 크게 표시해주세요. 일반적인 카드 Dashboard보다 공간 자체가 화면의 주인공이어야 합니다.

예시 공간: 회의실 A / 회의실 B / Open Desk A / Open Desk B / 라운지 / 리셉션 / 휴게공간 / 집중업무존

선택된 공간은 Orange Highlight 또는 Outline 등으로 명확하게 표시해주세요.

## 5. 공간 내부 구성 요소

공간 구성 History는 가구만 관리하는 기능이 아닙니다. 다음 요소들을 관리할 수 있어야 합니다.

가구 / 벽지 / 바닥 / 파티션 / 조명 / 문 / 천장·마감 / 시설·설비

예를 들어 "회의실 A"를 선택하고 그 안의 "회의 테이블"을 선택하면 우측에 Detail Panel이 표시됩니다.

## 6. 공간 구성 Detail Panel

```
[회의실 A] 회의 테이블 — 현재 상태
제조사     DESKER
모델       DSK-2400
구매일     2025.03.12
설치일     2025.03.18
구매 업체  OO Office
구매 금액  ₩1,850,000
상태       사용 중

[교체 사유]  기존 테이블 노후화 및 회의 인원 증가
[특이사항]  케이블 매립형 제품
```

"교체 사유"와 "특이사항"은 중요합니다. OFFICE HISTORY는 단순히 현재 어떤 물건이 있는지를 기록하는 자산관리 시스템이 아닙니다.

- "왜 이것으로 변경했는가?"
- "당시 어떤 문제가 있었는가?"
- "사용하면서 어떤 특이사항이 있었는가?"

같은 맥락까지 History로 남기는 것이 핵심입니다.

## 7. 공간 구성 History Timeline

선택한 공간 또는 구성 요소의 과거 변경 이력을 Timeline으로 보여주세요.

```
2023.03  회의실 최초 구축
  ↓
2024.01  회의실 확장 (8인 → 12인)
  ↓
2025.03  회의 테이블 교체 (노후화 / 사용 인원 증가)
  ↓
2026.06  조명 교체 (조도 개선)
```

각 History Event를 클릭하면 상세 정보를 확인할 수 있어야 합니다: 변경 전 / 변경 후 / 변경 일자 / 변경 사유 / 담당 업체 / 비용 / 시공 기간 / 관련 파일 / 특이사항

가능하면 Before / After 이미지도 History Event에 연결할 수 있도록 데이터 구조를 설계해주세요.

화면에는 최근 History 1~2개 정도만 우선 보여주고, "전체 History 보기"를 통해 전체 Timeline을 볼 수 있도록 구성해도 좋습니다.

정보가 많다고 해서 모든 정보를 한 화면에 노출하지 마세요.

> **"정보는 많지만 한 번에 보이는 정보는 적게"**

## 8. 공간 이용 History

두 번째 핵심 기능입니다. 이 화면의 질문: **"이 공간이 실제로 어떻게 사용되어 왔는가?"**

메인 화면은 **Floor Map + Usage Heatmap** 형태로 구성해주세요.

```
RED / ORANGE  이용률 높음
YELLOW        보통
BLUE          낮음
```

Floor Map 공간: 회의실 A / B / C, Open Desk A / B, 라운지, 집중업무존, 휴게공간

사용자가 공간을 클릭하면 우측 Usage Detail Panel의 데이터가 해당 공간 데이터로 변경되어야 합니다.

## 9. 공간 이용 Detail

```
[회의실 A]
현재 이용률     72%
평균 이용 인원  4.2명
평균 체류 시간  48분
Peak Time      14:00 ~ 16:00
```

그 아래에는 최근 이용률 추이를 Line Chart로 표시해주세요.

```
최근 6개월 이용률
APR 64% / MAY 67% / JUN 71% / JUL 69% / AUG 74% / SEP 72%
```

추가로 시간대별 이용 패턴을 Bar Chart 등으로 표시해주세요. (09-11 / 11-13 / 13-15 / 15-17 / 17-19)

## 10. 공간 이용 History 조회

현재 이용률만 보여주는 통계 Dashboard가 되어서는 안 됩니다. 과거 이용 History를 조회할 수 있어야 합니다.

```
2026.09.14
09:12  회의실 A  4명  42분
11:03  회의실 A  6명  55분
14:21  회의실 A  5명  63분
16:45  회의실 A  3명  31분
```

Day / Week / Month 단위 필터를 제공해주세요. 필터를 변경하면 그래프와 History 데이터가 함께 변경되도록 구현해주세요.

## 11. 공간 구성 History + 공간 이용 History 연결

**이 부분이 OFFICE HISTORY의 핵심 차별점입니다.**

공간 구성 History와 공간 이용 History를 서로 별개의 메뉴로만 끝내지 마세요. "공간이 변경된 시점"과 "실제 공간 사용 데이터"를 연결해야 합니다.

```
2026.06.01  회의실 A  8인 → 12인 회의실로 확장

[변경 전]  평균 이용 인원 4.1명 / 이용률 65%
[변경 후]  평균 이용 인원 4.3명 / 이용률 66%
```

이 데이터를 통해 담당자는 "공간을 12인 규모로 확장했지만 실제 평균 이용 인원과 이용률에는 큰 변화가 없었다."라는 판단을 할 수 있습니다.

즉 OFFICE HISTORY는 "무엇을 바꿨는가" 뿐만 아니라 "그렇게 바꾼 결과 실제 공간 사용이 어떻게 달라졌는가"까지 연결해야 합니다.

## 12. AI Insight

AI는 이 서비스를 지배하는 기능이 아닙니다. AI는 축적된 History를 해석하여 담당자의 판단을 돕는 보조 기능입니다.

AI가 함께 분석하는 데이터: 공간 구성 History + 공간 이용 History + 과거 Project History + 비용 History

```
[AI INSIGHT] 회의실 A
현재 12인 규모의 회의실이지만 최근 6개월 평균 이용 인원은 4.2명입니다.
4~6인 규모의 이용 패턴이 전체 사용의 78%를 차지합니다.
공간 효율성을 고려할 경우 12인 회의실 1개 → 6인 회의실 2개 구성을 검토할 수 있습니다.
```

AI는 확정적인 명령을 하지 않습니다. "변경해야 합니다."가 아니라 "검토할 수 있습니다.", "이러한 개선안을 고려할 수 있습니다." 같은 방식으로 표현해주세요.

프로세스: AI 분석 → 개선안 제안 → 담당자 검토 → 최종 의사결정

## 13. AI 공간 개선 Preview

AI Insight에서 개선안을 선택하면 공간 개선 Preview를 보여주세요. Before / Proposed 형태로 구성합니다.

중요한 점은 같은 공간과 **최대한 동일한 카메라 앵글**을 사용하여 비교하는 것입니다.

```
CURRENT 현재 공간   VS   PROPOSED AI 제안 공간
```

사용자는 실제 시공 전에 레이아웃 / 좌석 구성 / 공간감 / 이동 동선 / 회의실 구성 / 공용 공간 비율을 비교할 수 있습니다.

AI가 최종 CAD 설계를 자동으로 완성하는 것처럼 표현하지 마세요.

실제 프로세스: AI 공간 개선안 → 담당자 검토 → 설계 확정 → CAD 상세 설계

## 14. 예상 비용

```
[AI 예상 예산]  약 2,800 ~ 3,200만원
```

AI가 참고하는 데이터: 과거 시공 비용 / 자재 가격 / 업체 History / 과거 견적 / 유사 프로젝트 History

**중요**: 이 값은 실제 견적이나 확정 비용이 아닙니다. "의사결정을 위한 개산견적"입니다.

따라서 UI에 다음과 같은 안내를 표시해주세요.

> ※ History 데이터를 기반으로 한 참고용 예상 비용입니다.

가능하다면 근거도 간략하게 보여주세요.

```
유사 프로젝트  3건
평균 공사비    3,050만원
예상 범위      2,800 ~ 3,200만원
```

## 15. Project Asset

완료된 공간 프로젝트를 일회성 업무로 끝내지 않고 조직의 자산으로 축적합니다.

```
[PROJECT ASSET] 회의실 A 개선 프로젝트
Before / After
프로젝트 기간  2026.06.01 ~ 2026.06.15
비용          ₩31,200,000
업체          OO Interior
개선 결과      공간 이용률 +18%
```

전체 개념: PROJECT → HISTORY → ASSET → CASE STUDY / PORTFOLIO

과거 공간 개선 프로젝트가 이후 새로운 공간 프로젝트의 참고자료가 될 수 있어야 합니다. 보안상 공개 가능한 정보만 추후 Case Study 또는 Portfolio로 활용할 수 있다는 전제로 설계해주세요.

## 16. OFFICE HISTORY의 전체 데이터 흐름

```
공간 사용 → History 기록 → 데이터 축적
→ 공간 구성 데이터 + 공간 이용 데이터 연결 → 패턴 분석 → AI Insight
→ 공간 개선안 → 담당자 검토 → 실제 공간 개선 → 결과 다시 History로 기록
```

즉 서비스가 사용할수록 History가 쌓이는 구조여야 합니다. (사용 → 기록 → 분석 → 설계 → 개선 → 다시 기록 이라는 Flywheel 구조)

## 19. 디자인 방향

전체 UI는 **B2B Enterprise SaaS + PropTech + Digital Twin** 느낌으로 구현해주세요.

고급스럽고 전문적인 기업용 SaaS 느낌이어야 합니다. 저렴한 관리자 페이지처럼 보이면 안 됩니다.

**피해야 할 디자인**: 작은 카드 수십 개 나열 / 지나치게 많은 둥근 카드 / 과도한 Gradient / Neon / 과도한 Glassmorphism / 의미 없는 아이콘 남발 / 지나치게 큰 Border Radius / 모바일 앱 같은 UI / AI 서비스라는 이유로 보라색 Gradient

**색상**
- Background: White / Very Light Gray
- Primary Accent: ETNERS Orange 계열
- Text: Charcoal / Dark Gray
- Secondary: Light Gray
- Status: 필요한 경우 Green / Blue / Orange 등을 제한적으로 사용

## 24. 개발 시 주의사항

1. 처음부터 실제 AI API를 연결할 필요는 없습니다. AI Insight는 우선 Mock Data 기반으로 구현해주세요.
2. 실제 Backend와 DB 역시 첫 MVP에서는 필요하지 않습니다. Frontend Prototype을 우선 완성합니다.
3. 하지만 추후 Backend API를 연결할 수 있도록 Data Layer와 UI Layer는 분리해주세요.
4. 3D Office가 기술적으로 과도하게 복잡해진다면 첫 MVP에서는 실제 3D Engine을 구현할 필요가 없습니다. 고품질 Isometric Office Image 위에 Interactive Overlay를 배치하는 방식도 가능합니다. 중요한 것은 "3D 기술 구현"이 아니라 사용자가 공간을 선택하고 History를 탐색하는 경험입니다.
5. Floor Map 역시 처음부터 CAD Viewer를 구현할 필요는 없습니다.
6. 발표용 Prototype이므로 완성도 높은 UX와 시각적 품질을 우선해주세요.
7. 단, 화면만 예쁘고 실제 Interaction이 동작하지 않는 Prototype은 원하지 않습니다.
8. 각 화면의 기능이 실제로 연결되어 Demo Scenario를 수행할 수 있어야 합니다.

## 26. 가장 중요한 최종 요구사항

이 프로젝트의 핵심은 AI Dashboard를 만드는 것이 아닙니다.

OFFICE HISTORY라는 이름처럼 "공간이 어떻게 변했고" + "실제로 어떻게 사용되었는지"를 시간의 흐름에 따라 축적하고 서로 연결하는 것이 핵심입니다.

- 3D Office는 공간 구성 History를 탐색하기 위한 Interface입니다.
- Floor Map / Heatmap은 공간 이용 History를 탐색하기 위한 Interface입니다.
- AI는 축적된 History를 해석하여 담당자의 판단을 돕는 보조 수단입니다.

따라서 구현 과정에서 `AI > History`가 되어서는 안 됩니다. 반드시 `History > AI` 구조를 유지해주세요.

서비스의 핵심 메시지:

> "사무환경의 경험을 일회성 업무가 아닌, 다음 판단을 위한 데이터로."

OFFICE HISTORY의 궁극적인 방향:

> "개인의 센스를 조직의 데이터로."

이 철학이 실제 UI와 Interaction에서도 느껴지도록 설계해주세요.
